# Publication checks

These preemptive guardrails verify approved public attribution before new commits and pushes.

Initialized Windows Codex normally already ran `setup.ps1`, which installs the guard before restoring .NET dependencies. Reuse that policy and the provided default identity; do not rerun setup merely because a new task or skill starts. The autogenerated environment file does not need changes. Fresh checkouts need guard initialization before local commits; Node.js 18+ and Git are required. Other environments use the portable installer:

```sh
node scripts/codex/privacy-guard.mjs install
```

An unconfigured installation blocks commits and pushes. For the owner's web/cloud tasks, obtain the established public name and exact GitHub noreply email from existing owner-authored commits, not an arbitrary latest contributor/bot commit or an account-profile lookup. In Codex use the supplied default identity. Contributors/forks use their own approved public identity; never assign them the owner's identity. If initialization is needed, supply the established pair:

```sh
node scripts/codex/privacy-guard.mjs install --name PUBLIC_LOGIN --email ISSUED_NOREPLY_ADDRESS
node scripts/codex/privacy-guard.mjs check
```

Windows setup also accepts `-GitPublicName` and `-GitPublicEmail`. The current owner uses public name `SeyTi01`. The installer writes project-local `user.name`, `user.email` and `user.useConfigOnly`; unrelated global defaults remain untouched. Inspect worktree, author/committer, conditional-include and environment overrides if the resolved check fails. Do not work around a failure with per-command attribution that hides a broken default.

The policy, installed validator, original hooks and private settings backup live in the shared Git directory, outside tracked files. Installation is idempotent and applies to linked worktrees using default shared hooks. Existing pre-commit, commit-msg and pre-push hooks are preserved as `.privacy-original` and chained with their original arguments and complete stdin. A custom `core.hooksPath` or hook manager causes an actionable stop without changing its config or hooks; integrate the validator into that manager explicitly. Setup files alone do not install hooks in a checkout until setup is actually run.

`policy.json` contains exact approved `{ "name": "PUBLIC_LOGIN", "email": "ISSUED_NOREPLY_ADDRESS" }` pairs in an `identities` array. An additional public contributor or bot identity must be explicitly reviewed and added to this local policy; it is never inferred, broadly exempted or silently rewritten. Rerunning setup preserves these reviewed entries. Do not add personal addresses to make a rejection pass.

Pre-commit checks both identities Git actually resolves, including environment and command overrides and reused authors. Commit-msg checks `Signed-off-by` and `Co-authored-by` lines. Pre-push reads every proposed ref update, checks raw commit objects across the complete outgoing range, and validates newly published annotated taggers and identity trailers. Inspection disables replacement objects and rejects grafted history so local history views cannot hide outgoing metadata. Unsupported refs and tags not backed by commits fail closed. Deletions introduce no identities and are forwarded to existing hooks.

The publication boundary is the target remote's **currently advertised heads and tags**, queried during each push. Their reachable commit ancestry is already published and is excluded. A new branch with an all-zero remote tip still checks all newly introduced history; an unapproved intermediate commit cannot hide behind an approved tip. Cached tracking refs, dates and arbitrary last-N limits are never used as this boundary. All advertised objects must exist locally, and history must be complete. If inspection fails, fetch the remote's branches/tags and complete history before retrying. A changed remote advertisement fails rather than trusting an ambiguous range. Fetching does not authorize rewriting existing work.

Hooks are local and bypassable. They do not govern website/API writes or arbitrary identifying strings/images in source. GitHub's **Keep my email addresses private** and **Block command line pushes that expose my email** provide an additional account layer, but the latter checks the most recent commit's author email, not every author, committer, name, trailer or file. See [GitHub's documented scope](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/blocking-command-line-pushes-that-expose-your-personal-email-address).

Before owner-authored commits, run the resolved author/committer check. Before pushes/API publication, inspect all newly outgoing raw authors/committers, identity trailers, annotated taggers, messages, paths and changed content. Never bypass guards with `--no-verify` or disabled hooks. These checks concern new publication, not authorization to rewrite already-published history.

Prefer guarded local Git when CLI credentials are available. For this owner's established GitHub connection, API commit identity has already been confirmed and scoped API publication is authorized, including when CLI credentials or CI verification are unavailable. Local Git settings do not configure API identity: revalidate if the account, connection or API path changes. For an unverified route, use explicit approved author/committer controls or guarded Git; never publish probe objects to test defaults. Direct [Git commit API](https://docs.github.com/en/rest/git/commits#create-a-commit) requests support explicit identity objects. Verify published commit metadata and the intended tree. GitHub rebase/merge does not sanitize incoming authors; inspect them before authorized merges. See [API publication](../../plugins/ygo-work/skills/ygo-pr/references/api-publication.md) for transport and concurrency handling.

## Public content

Before publishing text, images or resource names, inspect for personal identities, machine paths and unrelated information. Inspect text and images separately; hooks cannot detect all identifying content. Never derive public hostnames, resources, documentation or screenshots from personal names/emails, machine profiles or billing data. Use the established public project identity. Content-only publication does not require local Git hook installation.

## Guard verification

Run the local-only integration tests with:

```sh
node --test scripts/codex/privacy-guard.test.mjs
```

They install the real hooks in disposable repositories and push only to local bare remotes. No negative fixture is uploaded.
