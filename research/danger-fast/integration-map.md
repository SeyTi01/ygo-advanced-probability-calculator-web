# Bounded-only result integration map

Source audit only; no production edits made. A useful solver is still a prerequisite. The current pipeline cannot truthfully accept a bounded-only primary by simply assigning an existing search certificate.

## Minimal explicit extension proposal

Add an optional immutable `Bounds` payload to `CalculationResultContract`, omitted from JSON when null. It contains exact-rational total/combo/group endpoints (one small interval record and one row container). **Its presence means no completed primary:** require `Fractions == null`, `SearchAvailability == null`, Fast execution, successful completion, Bounded accuracy, and a specific deterministic proof tag. Preserve the existing completed-primary/search-certificate variant unchanged.

Keep the existing numeric total/row fields as explicitly documented display centers for this variant. Derive them from the exact endpoint midpoint, never store midpoint or explored success mass in `CalculationFractions`. Presentation and exports must treat rational endpoints as authoritative. The variant itself must make the meaning of those numeric fields unambiguous; a small `ValueKind` discriminator is an alternative if the team prefers it to the `Bounds`/`Fractions` union.

Use a general base-only fixed-policy event reference for this payload, such as `Saved-effects fixed-policy success probability (v1)`. Existing `EffectsReference` comes from `CalculationCapability.Reference` and literally says **Deck-search target survival**; it is not truthful for unresolved draw/discard outcomes. Do not change the existing search certificate's mathematical meaning. When every endpoint is equal, produce the ordinary exact contract/fractions instead of preserving a bounded-only special case.

For fail-closed versioning without changing unaffected result JSON, reserve result-contract version 2 for the bounded-only variant and retain version 1 for existing variants. Validate that the version and payload shape agree. Update the browser owner's success-header recognition to accept the explicit version-2 shape. A global version bump is also viable but creates unnecessary fixture churn; silently permitting missing fractions on arbitrary version-1 success is not.

## Preservation requirements

- A completed certificate is `Completion.Success`, even when width is nonzero; a failed unfinished calculation remains the existing typed failure response with no bounds/fractions. Work exhaustion may return a successful certificate only if the solver has atomically preserved a valid partition and reserved finalization work.
- `Accuracy.Bounded` applies to every row of the same captured request; no row list may be reordered between bounds and displayed rows. Empty/disabled semantics must come from the existing row mapping.
- Existing Exact proofs, search certification, legacy/native constructors, numeric formatting, session/share inputs and .ydk behavior must keep their contracts. Ordinary session recovery saves workspace inputs, not these result certificates; this task does not require a session schema bump or partial-calculation persistence.
- The generalized guarantee is numerical enclosure of the base-only fixed-policy event. Omitted Danger discard triggers remain explicit model limitations, not part of the interval.

## Focused regression map

1. Reader: accept the new valid variant; reject missing rows/endpoints, invalid rationals, inverted/out-of-range intervals, forbidden primary/search fields, inconsistent version/reference/mode, and bounds on failure. Keep old `U <= primary` rejection tests.
2. Presentation/export: exact outward radius after printed-center rounding, no fabricated primary in evidence/focus/copied text, zero/one endpoints, per-row width and exclusion rows. Reuse `ProbabilityPresentationTest` and `ProbabilityResultExportTest`.
3. Lifecycle: initial Bounded Fast → Exact success, Work/Storage/error/cancel fallback, stale input and replacement worker ownership. Reuse `scripts/background-calculation/worker-policy.test.mjs`, `CalculationRecoveryTest`, and existing Progressive tests; controlled completion avoids timing assumptions.
4. Pins/language handoff: immutable exact endpoints, labels and context survive capture/restore; malformed bounds are rejected. Existing `PinnedResultTest`, `PinnedResultExactRetryTest`, and language checkpoint tests are appropriate.
5. Published stripped-AOT: actual worker result decode and display/pin/copy, cold/warm requests separately. Native-only serializer success does not establish the browser contract.

No integration tests were executed for this proposal because no production extension has been implemented. Lead owns local checkpoint commits; reviewer made none.
