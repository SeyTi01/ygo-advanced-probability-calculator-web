# Complete release promotion

Use only for a complete release task, after preparation. Reuse completed stages; enabling auto-merge or opening a PR is not completion. Keep monitoring in the current task until the next stage can proceed, or report a concrete blocker with the completed stages and remaining operation.

1. **Merge the version PR into `dev`.** Inspect its exact head, incoming identities under [publication identity](../../ygo-pr/references/publication-identity.md), required checks, unresolved discussions and mergeability. Refresh the task branch against `dev` when required and rerun invalidated checks. Current rules require a rebase merge into `dev`; re-read them rather than assuming the repository-wide merge settings apply. Guard the merge against a changed head. Verify the PR merged and the requested canonical version is present on remote `dev`.
2. **Merge `dev` into `main`.** Refresh both branches, create/reuse the release PR with head `dev` and base `main`, and inspect its complete diff and head. Current rules require a merge commit and passing application, published-site and Cloudflare checks. Wait for all required checks on the inspected head; a missing, pending or cancelled check is not success. Recheck changed PR heads and bases before merging. Never rebase, squash, force-update or delete shared `dev` as task-branch cleanup, or bypass protection to force a failed merge. If a conflict needs integration, preserve both shared histories through an appropriate PR; do not silently drop `main`-only changes.
3. **Resolve the release commit.** Confirm the promotion PR merged, then read remote `main` and its canonical version. Normally its tip is the returned merge commit; never use the pre-merge `dev` SHA or a stale local checkout. Inspect and verify any intervening commits before choosing a newer tip, refresh the notes range, and recheck `main` immediately before tagging. Wait for the final commit's CI. Follow its production deployment using [infrastructure](../../ygo-implement/references/infrastructure.md) and inspect deployment commit/version provenance; the pre-merge Cloudflare check alone does not prove production is running that commit. Honor any configured publication gate, but otherwise report a failed or unverifiable deployment separately from GitHub publication instead of inventing another release gate.
4. **Tag and publish.** Follow [GitHub publication](github-publication.md) to create the version tag at the verified `main` SHA, publish curated [release notes](release-notes.md), and explicitly make the normal stable release latest. Capture the predecessor before publication; do not recalculate it from an endpoint that now returns the release being created.
5. **Read back the result.** Verify both PRs are merged (or the corresponding preparation was already complete), the remote tag resolves to the chosen commit, that commit contains the requested version, and the Release is published with the correct body/compare link. For a normal stable release, require non-prerelease status and verify GitHub's latest endpoint returns that release; for an explicitly different release mode, verify that mode's publication/latest settings instead. Report the release URL and any material limitation concisely. Do not claim publication or production success from a successful command alone.

On retries, inspect PR/tag/release state before each write, including after an ambiguous network timeout. Never create duplicate PRs, repeat a version bump, force-move a published tag, or delete/recreate a Release to recover. A tag at the correct commit with no Release resumes at publication. An already-correct published Release is verified and reused. If another release has overtaken this task, do not reset the latest marker or promote an older version automatically; reconcile the concurrent release first.
